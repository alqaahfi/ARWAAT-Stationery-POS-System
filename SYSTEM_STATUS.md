# ARWAAT Stationery POS System — Current State

A full inventory of what's implemented in this codebase, written for someone picking up development from here. It describes **what exists and how it behaves**, not a code review — bugs/cleanup aren't called out except where explicitly noted as a known limitation in the code's own comments.

Generated by reading the full `src/` tree (migrations, every IPC module, every renderer page) as of the state described in the "Known gaps" section at the end.

---

## 1. What this is

An **offline-first, single-shop POS system** for a stationery/bookshop, built as a desktop app:

- **Electron** (main process = Node/SQLite backend, renderer = React UI)
- **React 19** (no router library — a hand-rolled `switch`-based router in `AdminDashboard.jsx`)
- **better-sqlite3** — one local SQLite file per PC (`userData/pos.db`), synchronous queries throughout
- **Vite** for the renderer dev server/build
- Plain inline-style React components driven by a single theme token file (`src/renderer/config/theme.js`) — no CSS framework
- **Multi-PC sync over LAN** (no cloud, no central server) — one Admin PC + any number of Cashier PCs on the same WiFi, syncing peer-to-peer

Run it with `npm run dev` (concurrently runs Vite + Electron); `npm run dist` builds a Windows installer via `electron-builder`.

## 2. Architecture

```
src/
  main/                     Electron main process (Node, has DB access)
    index.js                App bootstrap: DB init, IPC registration, sync startup
    preload.js              contextBridge — the only surface the renderer can call
    db/
      connection.js         SQLite connection + migration runner
      migrations/*.sql      025 sequential migration files (see §3)
      models/Product.js     Shared low-stock/dead-stock logic (single source of truth)
    ipc/*.ipc.js            One file per feature area, each registers its own channels
    license/                Machine ID, activation logic
    pricing/priceEngine.js  Price resolution (fixed/percentage/tier net-rate)
    ledger/balanceEngine.js Customer/supplier balance derivation (never stored)
    printing/               Thermal ESC/POS, A4 PDF-merge, report PDF export
    sync/                   Discovery (UDP), sync server (Express), sync engine, codec
    devpanel/               Audit middleware, session tracker
    activity/activityLog.js Cashier activity trail
    expenses/recurringExpenses.js  Recurring-expense materialization engine

  renderer/                 React UI (no direct DB/Node access — everything via window.api.*)
    app.jsx                 Top-level router: Setup → Login → Dashboard
    context/AuthContext.jsx Session + permission state
    layout/                 Sidebar, TopUtilityBar (global search, alerts, quick add)
    config/                 theme.js, navConfig.js (route map), appInfo.js
    pages/                  One folder per feature module (see §5 onward)
    components/             Shared UI kit (ui.jsx), DevPanel, receipt renderer

  shared/                   Plain CommonJS, imported by main only (renderer keeps its own
                             small copies where it needs the same constants, to avoid
                             pulling CJS into the Vite/ESM bundle)
    permissionDefinitions.js   Single source of truth for every cashier permission
    expenseRecurrence.js       Recurrence types + date-math (addPeriod)
```

**IPC pattern**: every `main/ipc/*.ipc.js` file exports a `register*Ipc()` function called once from `index.js`. Two pieces of middleware wrap `ipcMain.handle` globally, before any module registers its channels, so no individual module has to opt in:
- `installAuditMiddleware` (devpanel/auditMiddleware.js) — logs every call to `dev_audit_log`, redacting password/token/secret-shaped fields.
- `installSyncTriggerMiddleware` (sync/syncTrigger.js) — after any call, checks if `sync_outbox` grew; if so, schedules a debounced sync round with known peers.

**No React Router.** `AdminDashboard.jsx` holds `nav.route`/`nav.params` in local state and a big `switch` statement renders the matching page. `navConfig.js` is the sidebar's data-driven menu; `ROUTE_TITLES` derives page headings from it. A route present in `navConfig.js` but missing from the `switch` falls through to `PlaceholderPage.jsx` ("coming soon") — see §16 for which routes are currently stubs.

## 3. Data model (25 migrations, `src/main/db/migrations/001`–`025`)

Core tables (grouped by area — see the actual `.sql` files for exact columns):

- **Auth/Setup**: `settings` (shop-wide key/value), `users`, `user_permissions`, `sessions`, `license_activation` (single row, this PC's activation), `license_keys` (500-key activation pool, see §4)
- **Catalog**: `categories` (1-level parent/child), `suppliers`, `products`, `product_variants` ("Types"), `product_units` (selling units + prices + tier net-rates), `stock_movements` (full audit trail)
- **Customers/Pricing**: `customers`, `percentage_pricing_rules` (per-customer or per-tier margin-over-cost)
- **Sales**: `sales`, `sale_items`
- **Money**: `payments`, `ledger_adjustments`, `expenses`, `recurring_expenses`
- **Purchases**: `purchases`, `purchase_items`
- **Printing**: `letterheads` (PDF templates)
- **Sync**: `sync_outbox`, `sync_peer_state`, `sync_log` (see §14)
- **Ops/Diagnostics**: `activity_log`, `dev_panel_config`, `dev_audit_log`, `dev_panel_access_log`

Removed/superseded along the way (worth knowing so you don't go looking for them): `customer_categories` and `product_category_prices` (018 — replaced by the fixed C1–C5 tier system baked into `customers.tier` + `product_units.net_rate_c*`), `expense_categories` (021 — replaced by free-text `payee` + the `recurring_expenses` engine), `sync_queue` (022 — replaced by the trigger-driven `sync_outbox`).

**Soft-delete convention**: products, variants, units, categories, customers, suppliers, users, letterheads all use `is_active` rather than hard deletes, because sales/purchases/history may reference them. Purchases themselves are the one thing that's genuinely immutable once created — no edit or delete path exists for a purchase.

## 4. Licensing, Setup & Factory Reset — *this session's work*

This replaced an earlier Ed25519-signed, machine-locked license-key scheme entirely.

**Activation model**: `025_license_keys.sql` bakes a **fixed pool of 500 pre-generated keys** (format `XXXXX-XXXXX-XXXXX-XXXXX`) into every install. `licenseManager.activateAdmin()` does a plain local lookup (`is_used = 0`), marks the key consumed, generates a `sync_secret`, and writes `license_activation`. **Enforcement is per-installation only** — there's no server, so a different shop's install of the same app has its own identical copy of the same 500 keys and would independently accept the same key value. Discipline against handing the same key to two shops is the developer's responsibility (a private master list kept outside the repo).

**Setup flow** (`SetupAdmin.jsx`):
- Primary path: Shop Name + Activation Key + Station Code → activates, shows a one-time Sync Secret (needed later by every Cashier PC), then Create Admin Account.
- Secondary path: "Already have a backup? Restore instead." → picks a `.db` file, validates it actually has `license_activation` + `users` tables (opened read-only first), swaps it in, relaunches. Lets someone recover a whole shop's data without consuming a new key.
- **Resume-after-interruption fix**: if the app is ever closed/crashed between key activation and account creation (activation persisted, but no user row yet), `app.jsx` now detects this specific state (`license_activation` exists for an admin role but `hasAdminUser()` is false) and routes straight back to the Create Admin Account step — using the *existing* activation, not asking for another key.

**Cashier setup** (`SetupCashier.jsx`): just Station Code + the Sync Secret copied from the Admin PC's screen — no manual IP entry; the Admin PC is found via UDP auto-discovery (§14). `CashierInitialSync.jsx` then blocks on Login until a first real sync from Admin succeeds (a brand-new Cashier PC has no user accounts otherwise).

**Factory Reset** (Settings → Backup & Restore → Danger Zone, admin-only): wipes every business/transactional table plus `license_activation` in one transaction (with FK enforcement briefly disabled — several tables here have no `ON DELETE CASCADE`, so no delete ordering would otherwise avoid constraint failures), then relaunches to the Setup screen. **Does not** unmark the consumed `license_keys` row (a reset needs a fresh key) and **does not** touch `dev_panel_config`/`dev_audit_log`/`dev_panel_access_log`/`_migrations` (diagnostic history and schema bookkeeping survive a reset on purpose). Requires typing the literal word `RESET` to enable the button.

**Backup & Restore**: `backup:export` copies the live `.db` file out; `backup:restore` (from inside a logged-in session) and `backup:validate-and-restore` (from Setup, pre-login) both close the DB connection, swap the file, clean up stale `-wal`/`-shm` sidecars, and relaunch.

**`hasAdminUser()` bug fixed this session**: `seedDummyCashier()` runs unconditionally on every boot (seeding a demo cashier), so gating first-admin creation on "does any user exist" (`hasAnyUser()`) meant a fresh install always found a user already present and refused with "Setup has already been completed." Fixed by adding a role-specific `hasAdminUser()` check, used both by `createFirstAdmin` and by the resume-flow detection above.

## 5. Auth, sessions & permissions

- `users` table: `role` is a hard `admin`/`cashier` enum — **there is exactly one admin account**, created once during Setup; there is no UI path to create a second admin.
- Sessions: 7-day token in `sessions`, validated on app load from `localStorage` (`AuthContext.jsx`). Deactivating or resetting a cashier's password immediately revokes all their active sessions.
- Permission system (`src/shared/permissionDefinitions.js`, the single source of truth):
  | key | type | meaning |
  |---|---|---|
  | `make_sale` | boolean | access to the POS screen |
  | `view_products` | boolean | Products list + Low Stock report |
  | `record_payment` | boolean | standalone customer-payment screen (granted by default on every cashier) |
  | `max_discount_percentage` | number | per-cashier discount cap override; blank = falls back to shop default |
  | `view_sales_history` | boolean | (route not yet built — see §16) |
  | `view_reports` | boolean | Reports module |
  | `manage_expenses` | boolean | Expenses module |
  - Admin implicitly has every permission (`hasPermission()` short-circuits on role).
  - Some modules (Customers, Suppliers, Ledgers, Users, Settings) are **hard role-gated**, not permission-gated — a cashier can never see them regardless of any permission flag.
- **Activity log** (`activity_log`): one row per notable cashier action (login/logout/sale_created/etc.), viewable per-session in Cashiers → Session Activity → drill into a session.
- **Dev Panel**: a hidden diagnostic overlay, unlocked by clicking a near-invisible icon 5× within 3 seconds + a password. Read-only by design (every handler is a SELECT, enforced server-side against stacked statements and mutating keywords even inside CTEs), with `password_hash`/session `token` columns always masked. Tabs: Audit Log (every IPC call, auto-logged via the middleware in §2), Database Browser (table view + a locked-down SELECT-only query console, capped at 1000 rows), Users & Sessions, System Info, Access Log (unlock attempts against the panel itself).

## 6. POS / Sales (`pages/POS/Sale.jsx`)

A keyboard-driven "Cashier Mode" stage machine: `idle → customer → item-search → qty → cart-edit → discount → format → payment → confirm`. Highlights:

- **Draft autosave**: cart state persists to `localStorage` per station, debounced 400ms; resumable across restarts. The router guards navigating away mid-sale.
- **Customer selection**: optional (walk-in allowed for retail-paid-in-full sales only — a walk-in cannot carry a balance due).
- **Item entry**: debounced grouped search, or exact barcode scan-to-cart. Adding a line that matches an existing cart line (same variant+unit) merges quantities.
- **Pricing**: resolved server-side per line via the price engine (§7) at the moment it's added, and **re-resolved for every line** whenever the customer changes.
- **Discount cap**: enforced client-side on entry and **re-checked server-side immediately before finalizing** (permissions can change mid-shift).
- **Stock check**: quantity entry and finalization both block on insufficient stock — no negative-stock sales are possible through this screen.
- **Receipt format**: Wholesale (A4, via letterhead PDF-merge) or Retail (Thermal ESC/POS), independently chosen from customer type.
- **Finalize** (`sales:create`, one transaction): server recomputes the subtotal itself (never trusts the client's total), derives `payment_status` (paid/partial/unpaid), decrements stock + writes `stock_movements`, and — only for a *named customer* — writes a linked `payments` row for whatever was actually paid (a walk-in's payment is captured only in `sales.paid_amount`, no ledger entry). `sync_outbox` population happens automatically via DB triggers, not this handler.
- Invoice numbers: `{stationCode}-{YYYYMMDD}-{seq}` — per-day-per-station so offline PCs never collide before syncing.

## 7. Pricing engine (`main/pricing/priceEngine.js`)

One function, one precedence order (first match wins):
1. Per-customer percentage rule (cost × (1 + %))
2. Per-tier percentage rule (same formula, customer's tier)
3. Hardcoded tier net-rate on the unit (`net_rate_c1`..`net_rate_c5`)
4. Product-level percentage-over-cost (books/agency items, `pricing_type = 'percentage'`)
5. Fixed retail/wholesale list price on the unit (final fallback; walk-in always gets retail)

## 8. Ledgers, payments & customer/supplier balances

- **`balanceEngine.js`** is the single source of truth: a party's balance is **always derived**, never stored — `opening_balance + sales/purchases − payments + ledger_adjustments`.
- **Ledgers module** (admin-only): Overview (receivables/payables/advances totals + top-5 outstanding), Customer/Supplier Ledger (running-balance transaction history + inline Record Payment), Payment History (combined cross-party log with reprint), Advances & Credits (parties currently in credit), Aging Report (customer receivables bucketed 0–30/31–60/61–90/90+ days, explicitly documented as an approximation — ages each unpaid sale independently rather than FIFO-reallocating payments), Manual Adjustments (admin-only, requires a reason — the one place that writes straight into the balance formula outside of normal transactions).
- **Standalone payments**: `Record Payment` (permission-gated, so cashiers can use it too) for customers; a separate admin-only supplier-payment path. Overpayment is allowed but requires the operator to confirm via a dialog first.
- **Percentage Pricing Rules** management (`Customers/PercentageRules.jsx`, admin-only): target either one customer or a whole tier; only products with `pricing_type='percentage'` or `is_agency_item=1` are eligible.

## 9. Products, inventory & purchases

- **Product Form**: name/brand/category/supplier/min-stock-alert/dead-stock-days/notes/active/agency-item flag; "Types" (variants, each with its own barcode) and "Units" (selling units, each with conversion factor + cost/wholesale/retail price + optional per-tier net-rate overrides C1–C5). Editing a product never touches existing stock quantities — that's Stock Adjustments' job alone; removed variants/units are soft-deleted.
- **Bulk Import**: CSV, one row per product×variant×unit combination, grouped client-side by SKU/name; validated (category must already exist, SKU/barcode uniqueness checked live) with an all-or-nothing preview before a single-transaction import that reuses the exact same `create()` path as manual entry (no looser bulk path).
- **Low Stock / Dead Stock**: thresholds and status logic centralized in `db/models/Product.js` so the Product List's badges, the two dedicated report pages, and the Reports module's Stock Report can never disagree.
- **Stock Adjustments**: the one manual path (besides purchases and sales) allowed to touch `stock_qty` directly — requires a reason code (damaged/expired/lost/recount/other), decreases are bounded by current stock.
- **Movement History**: read-only audit trail over `stock_movements`, capped at 500 rows.
- **Purchase Entry** (admin-only): select supplier + line items (product/unit/qty/cost, cost fully overridable per purchase), one transaction increments stock and inserts `purchase_items`/`stock_movements`. **Purchases are permanent** — no edit/delete. Does **not** write back into the product's stored cost price. Supplier balance updates automatically since it's derived, not stored.
- **Suppliers** (admin-only): CRUD + opening balance (edit-locked after creation, same convention as customers) + its own simplified ledger view.
- **Categories**: one level of parent/child; delete blocked while any product still references it; name uniqueness enforced.

## 10. Customers, Reports, Expenses & Dashboard

- **Customers** (admin-only): retail/wholesale type, optional tier (C1–C5, fixed list), assigned letterhead (wholesale only), opening balance (edit-locked after creation). `searchMinimal` gives cashiers a restricted lookup (name/type/phone/balance only) for Record Payment.
- **Reports** (7 reports, one shared JSON envelope + shared UI components — `DateRangePicker`, `ReportSummaryCards`, `ReportTable`, `ExportButtons`, all with CSV + PDF export): Sales Report, Profit & Loss (bucketed by day/week/month depending on range length; **explicitly documented caveat**: COGS uses *current* cost prices, not historical — not snapshotted per sale), Stock Report (valuation approximated from the smallest-conversion-factor unit's cost price), Customer Statements, Supplier Statements, Cashier Performance, Expense Report. A cashier's own Sales Report is always scoped server-side to their own sales regardless of what filter they send.
- **PDF export mechanism**: a hidden `BrowserWindow` reloads the renderer bundle with a `?print=1` query string routing to a print-only view, then `webContents.printToPDF`.
- **Expenses**: one-time or recurring (daily/weekly/monthly/annually). Creating a recurring expense inserts both the first real occurrence *and* a `recurring_expenses` template; `generateDueRecurringExpenses()` (run at boot and before every read of `expenses`) **catches up missed periods** rather than skipping them, with date math that clamps month/year-end overflow correctly (Jan 31 + monthly → Feb 28/29). Recurrence type is locked after creation — "Stop Recurrence" ends the series without touching already-generated rows.
- **Dashboard**: role-split — cashiers get POS-only, no sidebar. Admin's `Overview.jsx` shows today's revenue/sales/low-stock/dead-stock tiles, a clickable revenue trend chart (drills into Sales Report pre-filtered to that day), and local active-session list. Note: the backend (`dashboard:get-summary`) already computes more fields (`totalProducts`, `totalCustomers`, `outstandingReceivables`, `monthExpenses`, `recentSales`) than the current UI renders as tiles.

## 11. Printing

Two real print paths plus a dev-mode fallback, all built from one shared data shape (`printing/receiptData.js`):
- **Thermal (retail)**: raw ESC/POS via `node-thermal-printer`, silent (no OS dialog), configurable printer + paper width (58/80mm) in Settings.
- **A4 (wholesale)**: if the customer has an assigned (or shop-default) letterhead with an uploaded PDF template present on disk, the invoice is stamped onto it as real vector text via `pdf-lib` (auto-paginating a multi-page item table, keeping the totals block from splitting across pages); otherwise falls back to a plain HTML invoice. Both go through a normal, visible OS print dialog.
- **Dev-mode**: retail sales open an on-screen receipt preview window instead of printing silently (no physical thermal printer in dev), with an "Export as Image" button.
- Receipt header/footer text is entirely free-text, admin-configurable (`Settings → Receipt Content`), applied uniformly to thermal receipts and every A4 invoice.
- Report PDF export is a separate, letterhead-independent path (§10).

## 12. Multi-PC sync (LAN, no cloud)

- **Discovery** (`sync/discovery.js`): UDP broadcast every 5s announcing `{machineId, stationCode, role, tcpPort}` — no manual IP entry anywhere. A peer not heard from in 30s is marked offline but never forgotten.
- **Transport** (`sync/syncServer.js`): every PC (not just Admin) runs a small Express server with one endpoint, `POST /sync/exchange`, authenticated by the shared `sync_secret` header (not encrypted — an explicitly documented limitation; TLS would close that gap but is out of scope).
- **What travels**: every synced table gets a `uuid` (local integer ids never leave a PC) via triggers added in `022_sync_foundation.sql`; every insert/update/delete on a synced table auto-populates `sync_outbox` via triggers, so no application code needs to know sync exists. `sync/syncSchema.js` is the single table-by-table config (`upsert` / `insert_only` / `stock_movement` semantics, FK-to-uuid mappings, which 3 tables support delete).
- **Conflict handling**: single-writer-per-record is the assumed norm; `stock_movements` are applied as **deltas** (dedup by uuid, then add the quantity) rather than overwritten, so an oversell that goes negative from concurrent edits is left visible on purpose rather than silently clamped.
- **Triggers**: debounced (4s) after any local write that grows `sync_outbox`, plus an unconditional 25s periodic sweep against every known peer.
- **Known limitation** (documented in code): letterhead PDF files themselves aren't synced, only the row pointing at a path — a Cashier PC would need the file manually copied over for its own printing to work.

## 16. Known gaps / not yet built

- **Sales History & Returns/Refunds** (`/sales`, `/sales/returns`) are wired into the sidebar (`navConfig.js`) and have a dedicated permission key (`view_sales_history`) already defined, but there is **no page component** for either — both currently render `PlaceholderPage.jsx` ("coming soon").
- **Dashboard**: several backend-computed summary fields (`totalProducts`, `totalCustomers`, `outstandingReceivables`, `monthExpenses`, `recentSales`) aren't yet surfaced as tiles in `Overview.jsx`.
- **Profit & Loss** uses current cost prices for COGS, not a historical snapshot per sale — explicitly flagged in-app as a future-accuracy item.
- **Aging Report** methodology is a documented approximation (per-invoice aging, not FIFO payment reallocation), and exists for customers only — no supplier-side aging.
- **Categories** only guard against direct self-parenting; a deeper circular chain (A→B→A) isn't checked.
- **Sync** has no encryption in transit (shared-secret auth only) and doesn't sync letterhead PDF files, only their DB row.
- **No test suite.**
- **Single admin account only** — no UI path exists to create a second admin.
